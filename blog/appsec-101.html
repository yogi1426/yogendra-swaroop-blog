Getting Started With Web Application Security

A practical starting point for web application security — how to think about it, what to learn first, and where most beginners go wrong.

Jan 10, 2020 6 min read

Every security engineer I know got here the same way: by getting curious about how something actually works, then getting more curious about how to break it. Web application security is usually where that curiosity turns into a career — the attack surface is huge, the tooling is accessible, and the feedback loop is fast. Here's how I'd start if I were doing it again.

Think in terms of trust boundaries, not tools

It's tempting to start by installing Burp Suite and running a scanner against a test app. Do that eventually, but first spend time understanding why web apps break: every request crosses a trust boundary — browser to server, service to service, user input to a database query — and vulnerabilities live at the seams. Once you can spot a trust boundary, you can reason about what could go wrong there, tool or no tool.

Learn the fundamentals before the framework

You don't need to memorize every OWASP Top 10 CVE writeup on day one. You need:

  • HTTP itself — methods, headers, status codes, cookies, sessions. Most bugs are just HTTP behaving in a way the developer didn't expect.
  • Authentication vs. authorization — knowing who you are is not the same as being allowed to do something. Most real-world access-control bugs come from conflating the two.
  • Input handling — where user-controlled data enters the system, and every place it's later trusted without re-validation.

The OWASP Top 10 is a map, not a checklist

Use it to understand categories of failure — injection, broken access control, security misconfiguration — rather than memorizing definitions. Then go find each category in a deliberately vulnerable app (DVWA, WebGoat, PortSwigger's Web Security Academy) and actually exploit it. Reading about SQL injection and writing a payload that dumps a table are very different levels of understanding, and only one of them sticks.

Build a repeatable methodology

Beginners tend to click around randomly looking for bugs. Instead, build a checklist you run through every time: map the app's functionality, identify every place it takes input, note every place it makes a trust decision (auth, authorization, redirects, file access), and then test each systematically. A boring, repeatable process finds more bugs than random poking — and it's the same instinct you'll later need for threat modeling and secure design review, which is where the real leverage is.

Where most beginners go wrong

  • Jumping straight to automated scanners and trusting the output without understanding what triggered a finding.
  • Only ever testing intentionally vulnerable labs and never reading real-world disclosed reports (HackerOne/Bugcrowd public reports are excellent, free training data).
  • Treating security as a separate phase instead of a property of good engineering — the best appsec engineers I know are also just strong engineers.

Start small, stay curious, and build the habit of asking "what happens if this input isn't what the developer expected?" every time you look at a form, an API, or a URL. That question, asked consistently, is most of the job.
