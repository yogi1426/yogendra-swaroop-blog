Setting Up MFA on AWS the Right Way

Why root-account MFA alone isn't enough, and how to actually enforce multi-factor authentication across an AWS organization.

Feb 15, 2020 5 min read

Almost every AWS security checklist starts with "enable MFA on your root account," and almost every team stops there. That's a good first step, but it's a tiny fraction of what MFA actually needs to cover in a real AWS environment. Here's what a proper MFA setup looks like.

Start with the root account — but don't stop there

The root account can do anything, including deleting your entire account, so it must have MFA — ideally a hardware key (like a YubiKey), not just an authenticator app, since the root account is the one place a compromise is truly catastrophic. But root should barely ever be used day-to-day anyway; the real work is securing every IAM user and role that is used daily.

Enforce MFA for IAM users, don't just enable it

"Available" and "enforced" are different things. A permissive IAM policy that merely allows a user to enable MFA does nothing if they never do it. Use an IAM policy condition to deny actions unless MFA is present, something like:

{
  "Effect": "Deny",
  "NotAction": [
    "iam:CreateVirtualMFADevice",
    "iam:EnableMFADevice",
    "iam:ListMFADevices",
    "iam:ResyncMFADevice",
    "sts:GetSessionToken"
  ],
  "Resource": "*",
  "Condition": {
    "BoolIfExists": {
      "aws:MultiFactorAuthPresent": "false"
    }
  }
}

This lets a user manage their own MFA device but blocks everything else until they've set one up — a self-service enforcement pattern that scales far better than chasing people manually.

Use Service Control Policies at the organization level

If you're running AWS Organizations, push MFA enforcement up to an SCP so it applies uniformly across every account and can't be quietly removed by an account admin. This is the difference between "MFA is our policy" and "MFA is structurally impossible to bypass."

Prefer federated identity over long-lived IAM users

The best way to "enforce" MFA at scale is to remove the need to think about it per-user: federate through SSO (AWS IAM Identity Center, Okta, Azure AD) where MFA is enforced centrally at the identity provider, and stop creating standalone IAM users with console passwords entirely. Fewer long-lived credentials means fewer places MFA can be skipped — and it's the same principle behind the org-wide SSO enforcement work I've done professionally: treat MFA as an architecture problem, not a per-account checkbox.

Don't forget programmatic access

MFA conversations usually stop at console login, but access keys used by CLI/SDK calls are just as sensitive. Require MFA for sts:GetSessionToken and use short-lived session credentials instead of long-lived access keys wherever possible — a leaked temporary session token expires; a leaked static access key doesn't.

The takeaway

Root account MFA is table stakes. Real protection comes from enforcing MFA structurally — through IAM conditions, SCPs, and federated identity — so that "did everyone remember to turn it on" stops being a question you have to ask.
